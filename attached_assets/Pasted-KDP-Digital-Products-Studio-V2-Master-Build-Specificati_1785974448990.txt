1. Non-Negotiables (why this project exists — do not violate these)
No copyrighted or hired-writer content. This project exists specifically to avoid the cost/complexity of hiring writers and clearing copyright/publishing rights. Every product must be either: (a) low-content (structured templates: journals, planners, trackers, log books), or (b) medium-content that is 100% originally generated by our own system (prompts, layouts, structured fields) — never scraped, never copied from another publisher, never AI-hallucinated "facts" presented as authoritative content.
No duplicate-content strategy. Do NOT build a feature that takes one book and outputs 5–10 near-identical copies with only the cover color changed. As of 2026, Amazon KDP actively suppresses/removes books like this. Every generated variant must differ in at least one of: target audience, structural content (different sections/fields, not just color), or page count/format — not color alone.
Every generated interior must pass the margin-safety rule automatically, not by manual patching after KDP rejects it: MARGIN = 0.4in on all sides, nothing (text, shape, banner, background) may touch or cross x=0, y=0, PAGE_W, PAGE_H. This must be enforced by a reusable validation function that runs on every page before file output, and the build should refuse to export a PDF that fails this check (fail loudly, not silently).
Minimum page counts must be enforced by the generator itself, not discovered via KDP rejection emails: 72 pages minimum for color interior, spine text only permitted when page count ≥ 79. The tool must warn the user before generation if their chosen day-count/page-count would violate this, and suggest a fix (e.g. "60 days → pad to 73 pages" logic already proven in the old script).
User is not a developer. Every user-facing screen, button, and message must be understandable without coding knowledge. No raw JSON, no stack traces, no technical jargon in error messages — translate errors into plain instructions ("Page 14 has a shape that's too close to the edge — auto-fixing it now" instead of "ValueError: y_coord out of bounds").

3. What NOT to Build (explicitly out of scope for V2)
Do not build a "color variation generator" that mass-produces near-identical books (see Non-Negotiable #2).
Do not build user accounts / multi-tenant login system unless explicitly requested later — this is a single-user internal tool for now.
Do not integrate direct KDP auto-upload/auto-publish via unofficial scraping or automation of Amazon's site — Amazon's ToS prohibits this and it risks account suspension. Manual upload by the user remains the final step; the tool prepares 100%-ready files only.
Do not over-engineer a generic "any query becomes a tool" system. Build the specific features requested in Section 4, not speculative extras.


4. New Capabilities for V2
4.1 Design Upgrade
The old UI was described by the user as "too simple." Apply the frontend-design design principles: intentional typography, real visual hierarchy, no default/templated look. This applies both to the tool's own dashboard UI and to the generated book covers/interiors themselves.
4.2 Image Generation
Integrate an image-generation step into the cover/interior pipeline (the old tool already showed this working during testing — formalize it into a proper pipeline step): given a book's niche + palette, generate supporting icon/illustration assets, not just flat color shapes. Cache generated images per template so re-generation doesn't re-spend image credits unnecessarily.
4.3 Progress/Plan Tracker ("Memory Agent" — Tracker Mode)
Build a persistent PROGRESS.md-style tracker (same pattern as the BioMinute project's Excel tracker) inside the repo:

One row/entry per planned feature or book, with a checkbox state: Not Started / In Progress / Done
Update this file automatically as work completes — don't leave it stale
This file is the first thing a future session (human or agent) should read to know what's already done
4.4 Niche & Content Strategy Module
Given the 2026 policy tightening around duplicate content, build a lightweight niche-validation checklist into the tool itself (not just a doc): before generating a new book, the tool should prompt the creator to confirm the book has genuine structural differentiation from any prior book in the library (different fields, different audience, different depth) — not just a new color.


5. Output Format Definition
For every generated book, the tool must produce:

[Title]_Interior.pdf — print-ready, margin-validated interior
[Title]_Cover.pdf — print-ready cover matching the exact KDP Cover Calculator dimensions for that page count
[Title]_Listing.md — KDP listing metadata: title, subtitle (checked against KDP's "no repetitive keyword stuffing" rule — see Section 6), description, 7 keywords, 2–3 real category paths, suggested price
An entry added to PROGRESS.md marking the book as generated (not yet "published" — that stays a manual, user-confirmed step)


6. Hard Lesson From the Old Repo — Title/Subtitle Rule
A real KDP rejection occurred because a subtitle listed too many features ("...with Time Blocking, Mood Tracker & Habit Tracker for Focus and Productivity") — Amazon flagged this as keyword stuffing. The metadata generator (Section 5, item 3) must enforce: subtitles state the core value proposition in one clause, not a feature list. Feature lists belong in the description only.


7. Git / Push Rules
Commit after each logically complete unit of work (a working feature, not mid-edit).
Every commit message format: <type>: <short description> where type is one of feat, fix, refactor, docs. Example: feat: add image generation step to cover pipeline.
Do not squash history into a single commit before pushing — keep incremental commits so future debugging/review is possible.
Update PROGRESS.md in the same commit as the feature it tracks, not as a separate cleanup pass later.
Never commit .env or any file containing credentials — confirm .gitignore includes .env, .env.local, and any API key files before the first commit.
Push to main only when the app builds and the previous feature's tests (if any) pass — do not push broken intermediate states.
